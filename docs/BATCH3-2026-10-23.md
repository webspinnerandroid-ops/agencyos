# Batch 3 — hardening (2026-10-23)

The structural items from the Round-20 audit, done as far as they can be done
safely in one pass: tenancy got a real gate instead of a decorative policy, and
body validation got a helper, two migrated routes and a ratchet so it can't
regress while the rest migrate.

## 1. Tenancy: RLS was decorative — now the gate is real

**What the audit found:** every table has a `tenant_isolation` policy shaped
like `tenant_id = (auth.jwt() ->> 'tenant_id')::uuid`, but nothing ever sets that
claim (no Supabase auth hook, no `app_metadata` write). For anon/authenticated
tokens the predicate is `tenant_id = NULL`, so the policies **deny every row** —
and the app runs on the service role, which bypasses them entirely. Isolation
has always come from `.eq("tenant_id", …)` in application code. The QA suite
proved the deny side: a tenant's own user reads zero rows through PostgREST.

**Decision taken:** keep the policies as deny-by-default (they cost nothing and
block accidental anon reads), stop describing them as the isolation mechanism,
and make the actual mechanism enforceable. Setting a real JWT claim would mean
rewriting every request path off the service role — a much larger change than
this batch, and not needed while the static gate holds.

**Shipped:**

- `scripts/audit-tenant-scope.cjs` now covers the tables added by later
  migrations (`tenant_balances`, `token_ledger`, `workflow_state`, `activity`,
  `content_map_*`, `site_pages`, `machine_api_keys`, …). Before this it silently
  skipped the newest and least-reviewed code: the set stopped at the tables that
  existed when it was written.
- That took the scan from **0 findings to 45**, across 24 files. I read every
  one. All 45 are safe-by-design patterns the heuristic cannot see: payloads held
  in a variable (`insert(patch)` where `patch` carries `tenant_id`), writes keyed
  by an id that came from a tenant-scoped read two lines above, capability-token
  lookups (`key_hash`, approval/signing tokens, `[Re:#<id8>]`), platform
  singletons (`site_settings` row id 1, super-admin only), and public-by-design
  surfaces (published site page by slug, public form widget that derives the
  tenant from the page row).
- Each became a **per-`file::table` reviewed exception with its reason**, not a
  whole-file exemption. The file keeps being audited; only that table is exempt.
  `IGNORE` (whole file: cross-tenant job workers, webhooks) is unchanged.
- The scan now reports `scoped / reviewed / cross-tenant-files / unscoped`, and
  fails (exit 1) on anything unreviewed. Proven by planting a synthetic unscoped
  query in `src/` — it was flagged and exited 1 — then removing it (exit 0).
- CI runs it as its own job, so a new route that forgets the filter fails the
  build rather than shipping.
- `ARCHITECTURE.md` no longer claims RLS provides isolation. It documents what
  the policies do, why a signed-in PostgREST read returns zero rows, and what a
  real second line of defence would require.
- Removed `getSupabaseWithTenant()` from `src/lib/auth.ts`. It had no callers and
  advertised "queries guaranteed to stay within the caller's tenant" through RLS
  — a trap for the next person, since the claim it relied on is never issued.

## 2. Body validation: helper + first family + ratchet

94 write routes read `await request.json()` and destructure it; 2 validated
anything. Migrating all 94 at once is a rewrite, so this batch establishes the
pattern and locks the direction of travel.

**Added `src/lib/api-validate.ts`:**

- `parseJsonBody(request, schema)` → typed data or a consistent 400:
  `{ error, code, issues: [{ path, message }] }`.
- 256 KB body cap (413), empty body rejected instead of parsing as `null`,
  malformed JSON rejected with `invalid_json`, no unhandled throws.
- `validateJson(raw, schema)` is the pure core — unit-testable without Next.

**Schemas** in `src/lib/validations.ts` (zod was already a dependency):

- `clientCreateSchema` — trims the name, accepts `""`/`null`/bare domain for
  website (the UI's own placeholder invites `acme.com`), caps notes.
- `postUpdateSchema` — enum of the real lifecycle statuses, offset-qualified ISO
  for `scheduled_at`, uuid-or-null `workspace_id`, non-blank `revision_reason`,
  and a refine so an empty PATCH is a 400 instead of a silent 200 no-op.

**Routes migrated:** `POST /api/clients`, `PATCH /api/posts/[id]`.

**Ratchet:** `scripts/audit-validation.cjs` counts validated vs unvalidated write
routes against a baseline (currently 4 validated / 90 unvalidated). A new
unvalidated route fails CI; so does losing a validated one. Migrating a family
means lowering the baseline in the same change — a deliberate, reviewable edit.

| `npx playwright test saas-qa-ui client-role-gate` | 24/24 passed |

The API contract tests prove the migration is not just types: `POST /api/clients`
with `{}` answers 400 with `issues[0].path === "name"`, the form's real payload
answers 201, `PATCH /api/posts/:id` with `{}` or a naive timestamp answers 400,
and a genuine `{ status: "approved" }` still returns 200 **and** lands in the
database.

One harness fix along the way: the register-form test clicked before hydration on
a cold compile and failed once; it now waits for `networkidle` and an enabled
submit button.

## Still open

- **90 write routes** still destructure an unvalidated body. The ratchet keeps
  that number honest; client/site/asset families are the natural next ones.
- **RLS remains deny-by-default**, not isolation. If a real second line is
  wanted, it needs an auth hook that stamps `tenant_id` into the JWT plus
  removing `service_role` from request paths.
- **Migration 106** (7 tables) from Batch 1 is still unapplied — it needs one
  paste into the Supabase SQL Editor.
